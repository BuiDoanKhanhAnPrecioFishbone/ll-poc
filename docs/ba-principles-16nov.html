Flagged — please settle these with her

1. Date and date-time column widths

RoleHersOurs
col-date110px150px
col-datetime170px190px

Not adopted, because tokens.ts carries the reason in a comment and the reason is a measurement of the live system:

The live Part Master renders LAST CHANGE as 09/09/2026 16:35:29 and the MPN list renders LAST SYNCED AT the same way, so a column that carries a timestamp needs room for one — 150px fits "16 May 2026" and clips the time off the end of it.

Her widths assume the numeric format 11/14/2026 and 11/14/2026 09:14 AM. If that format is now settled for every date column, her numbers are right and ours are oversized — but the date format itself is still listed as unresolved (see below), so changing the width before the format would be building on the thing that moves.

Question for her: is 11/14/2026 the format for every date column, including LAST CHANGE and LAST SYNCED AT?

2. Which Kendo step control-row sits on

She writes control-row 26px … (Kendo sm). This system's sizing page says the same 26px is Kendo's xs step. The value agrees; the name of the rung does not, and one of the two is wrong in a way that will mislead whoever next configures the Kendo size scale.

Checked and matching

Type scale (all nine steps, and the touch column rises exactly 2px for 2xs–lg as ours does) · the whole spacing scale including the gap where space-13 would be · motion, all four curves and three durations · control-md 34px · control-row 26px · target-min 44px · shell 248 · 56 · 52 · popup 640 · 960 · 1180 · column roles ident 240, text 280, code 96, number 104, money 124, status 128, priority 104 · the icon set at 45.

One difference that is not a conflict. Her type scale gives 2xs 10px and xs 11px and says they are "not used on desktop, below the 12px floor"; ours sets both to 12px outright. Same result on screen, and hers states the reason better.

Status words. She names seven business statuses — New · In Progress · Quoted · Waiting for Approval · Completed · On Hold · Cancelled. This system has eight --vy-status-* token pairs. These are different lists, not a disagreement: hers is the vocabulary a user reads, ours is the palette it is drawn from. It also explains a confusion already recorded here — Badge.tsx says "seven-token vocabulary" while B1.6 says "eight statuses", and both are right about different things. Worth asking her which token each of the seven words maps to, and writing that mapping down.
