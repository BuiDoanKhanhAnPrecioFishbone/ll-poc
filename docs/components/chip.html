Chip

Status: trial — two call sites, both selected, one screen. The unselected state is correct now but has still never shipped, so it has not been in front of a real user. Written to the template set by button.md. src/ui/Chip.tsx · specimen at /design-system

When to use

To show a filter that is currently on, and to let the user take it off in one click. Today that is the queue filter and the customer filter on Quotations — you arrive with the filter already applied, and the chip is how you get rid of it.

When not to use

Instead of a chipUseWhy
Showing a state the user cannot changeStatus badge or .vy-pillA chip is a button. Anything that is not operable must not look operable
Choosing one of several optionsRadio, or a selectA row of chips reads as several independent on/off filters, not one choice
An actionButtonA chip toggles a value; a button does something
More than about six filters at onceFilterToolbarPast that the chips wrap and the row stops being scannable

Anatomy

PartRule
Container<button type="button">, --vy-shape-sm, 1px border. Not a <div> with a click handler — it has to be reachable and operable from the keyboard
Check13px, leading, aria-hidden. Present only when selected
Label--vy-text-base. --vy-weight-medium when selected, regular when not

Selected is three things at once: a tonal fill, a blue border, and the check. Never colour alone, so the state survives greyscale and colour-blindness — the same rule the status vocabulary follows.

Why the border carries the contrast requirement

The selected fill is --vy-brand-subtle, which measures 1.11:1 against the page — effectively white. So the fill is not what tells you the chip is there; the border is, and WCAG 1.4.11's 3:1 applies to it. blue-300 measured 2.50 and would have failed. blue-400 clears it, so this needed no new token — unlike the grey scale, the blue scale had a conforming step already.

That was found while verifying the border token, not by the contrast sweep: the chip renders on one screen, conditionally, so it was on neither page the sweep walked.

Two defects the resting state was hiding — fixed 8 Nov

Neither could bite, because the unselected state never rendered — both call sites pass selected. Both would have bitten the first time somebody rendered a chip the user can switch on. Drawing that state on the specimen page is what found them.

1 · The resting border was 1.64:1. It used --vy-border-strong, which B1.4 defines as structure — panel edges, table rules — explicitly the category WCAG 1.4.11 does not cover. A chip is something you operate, so its boundary is the category that is covered, and --vy-border-control is the token measured for that job.

BeforeAfter
Resting border, light1.64:13.06:1
Resting border, dark—3.83:1
Selected border, light / dark4.48 / 3.82unchanged
The comment above that rule reasons carefully about the selected border — why blue-400 and not blue-300 — and says nothing about the resting one. That is how it survived: the question had been asked once, about the other half of the control.
The chip was not the only one. A sweep of every focusable control on 12 routes found six more using a structure token as a control boundary. .vy-rt-swatch was fixed the same day — a 20px button whose whole content is a colour fill, one of them transparent, so the border was the only thing showing there was a button there at all. The rest, including the Kendo outlined button, are listed in vien-control-08nov.md.

2 · aria-pressed disappeared when unselected. aria-pressed={selected} with selected undefined renders no attribute at all, so the chip was announced as a plain button: a screen-reader user was told there is a filter and not told it is off. false is a different statement from absent. Now aria-pressed={!!selected}, which renders "false".

Content

  • The label is the filter, not an instruction: Due this week · Mine, not Filter by due date.
  • Two facts in one chip are joined with · , as in the queue chip, which carries the queue name and the scope.
  • No count inside the chip. A count belongs to the thing being filtered.

Behaviour

  • onClick removes the filter at both call sites. The chip is a filter you take off, not one you put on.
  • Keyboard: Enter and Space, as for any <button>.
  • Hover and press come from data-state-layer, the same one rule every control in the system uses — nothing invents its own hover.

A naming mismatch worth settling

The comment in Chip.tsx calls this an MD3 input chip. In MD3 an input chip is the one with a trailing remove ✕; the leading check is a filter chip. This component is drawn as a filter chip and behaves as an input chip — clicking it removes the thing. Both readings are defensible, but the name should match one of them, because the next person will build the other kind from this file.
