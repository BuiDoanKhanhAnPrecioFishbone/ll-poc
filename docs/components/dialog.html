When to use

When the user must deal with one thing before carrying on: a question, a short form, or a work surface too big to sit inside the record.

Three sizes, and the default to open maximised

SizeWidthOpens maximisedFor
md640pxNoA question: a confirmation, a short form
lg960pxYesTwo blocks and a short table
xl1180pxYesA work surface: a 21-column grid, a four-step wizard

lg and xl default to maximised since 13 October, asked for at the meeting: "open one modal/dialog now open full size first."

Measured on 6 Oct: Run Quotation asked for 625px of scrolling on a 1920px screen while leaving 740px of that screen empty, because the dialog was a fixed 1180px at every screen size. The customer's own window for this flow fills the screen, and their reviewers said ours was small beside it. They were describing arithmetic.

md never maximises. One that fills a 27-inch screen to ask are you sure is a worse answer than the one it replaced.

Maximize is built; Minimize is not

Both are in the customer's guideline — "Allow user to use modal window actions: Minimize · Maximize/Restore Down · Close" — and only one is here.

Maximize earns its place. Run Quotation's pricing grid has fourteen columns, and filling the screen with it is the difference between reading the table and scrolling it sideways.

Minimize is deliberately absent. In Kendo it collapses a draggable window to its title bar, in place. These dialogs are centred and modal, not draggable, so a minimised one would be a title bar floating in the middle of a dimmed screen — which does not do the thing minimising is for. What a user wants there is to see the list behind, and Close already does that without losing anything, since nothing here is a long-running form.

Raised as question 9 rather than guessed at. If their users minimise dialogs to compare against the list underneath, the answer is a non-modal draggable window — a different component, and worth knowing before it is built.

Stacking, and the bug that was invisible

This app stacks dialogs three deep: a Part record opens a Stock Report, which opens Update Quantity. Every one of them used to carry the same z-index, as did every scrim. Two consequences, both invisible until you look:

  1. The innermost dialog was on top only because its portal mounted last. Correct by accident is the same fault that once put an error toast behind the Run Quotation dialog.
  2. A child's scrim could not dim its parent, so three stacked dialogs all rendered at full brightness with nothing to say which one was live.

Each level now steps its own scrim and panel above the level before it, through a depth context.

Rules

  1. Actions top-left on a work surface, in a footer on a question. The way out goes on the left wherever the bar sits.
  2. Escape dismisses the innermost thing — which Select had to be taught by hand, because Kendo's own handling closed the dialog from an open dropdown.
  3. The dismiss never repeats the confirm's verb. See Destructive action.
  4. A dialog has a title that names the record, not just the action — Discard changes to RFQ0000000358?, because on a screen this deep the record number is the fastest answer to which one.

Accessibility

FocusTrapped inside, returned to the trigger on close
EscapeInnermost first
ScrimEach level dims the one beneath it, so the live layer is visible as well as focusable
TitleThe accessible name of the dialog
BusyWhile a confirmed action runs, both buttons disable — leaving mid-write is how a record ends up changed with nobody watching
