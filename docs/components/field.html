Field

Status: stable · src/ui/Field.tsx · 91 call sites — the most used component in the product. Written to the template set by button.md.

Three controls in one file, because they are one idea wearing three shapes: TextField, TextArea, SearchField.

When to use

ControlFor
TextFieldOne line of typed text, a date, a number
TextAreaProse the user writes — notes, a description
SearchFieldNarrowing a list by a value the user already knows

When not to use

Instead of a FieldUseWhy
Choosing from a known listSelectA field that accepts anything cannot accept only what exists
A value this screen does not ownA read-only box with a padlockD2: grey means not editable, and the padlock carries the reason
A yes/noCheckboxA field for "Yes"/"No" is three ways to be wrong
Filtering a listFilter toolbarSearch finds a record you can name; filters describe a set

Anatomy

A <label> wrapping everything, so the whole thing is one hit target and the label needs no for.

PartRule
LabelAbove the value, never beside it. Title Case, 12px, 600
RequiredA red asterisk right after the label, in view and edit mode
OptionalNo mark. Never the word (optional)
Input--vy-border-control in edit mode; a sunken box in view mode
HintBelow the field, italic, at or below the label's size

A hint is a sibling of the label, never inside it — inside, it joins the accessible name and gets read as part of the field's title.

A hint and an error never appear together. Two lines, each claiming to say what to do next, is one line too many.

Errors arrive on blur

Not on every keystroke. A field that goes red while you are still typing the third character of a part number is telling you that you are wrong before you have finished being right.

The message is red text below the field — and wherever the system settles that placement, the timing does not change.

SearchField is its own component on purpose

Search is the single most-used control on every list screen and must look identical on all of them.

It is a type="search" input with a leading magnifier, and it is the one field with no label — the icon and the placeholder carry it, which is only acceptable because the control is in the same place on every screen.

ref is declared, not inherited

React 19 passes ref to a function component as an ordinary prop, but InputHTMLAttributes does not carry it, so TypeScript rejects it.

It is declared because Login needs it: to put the cursor in the first field, and to send it back there when a submit finds the field empty.

The three edges, measured

.vy-input draws its own boundary in three states, and all three are 1.4.11's business. On the panel, transitions stopped:

resthoverfocus
light3.975.246.82
dark4.045.239.58
Two of those six numbers were wrong until 9 November, and both only in dark. :hover pointed at --vy-border-heavy — darker than the resting border on white, lighter than it is what dark needs — so the hover edge measured 2.68 on the panel and 2.02 on surface-strong: fainter than the state it replaced, and under the threshold. :focus pointed at --vy-brand-boundary-strong, which kept blue-400 at 2.88 after the note beside it had already measured that number and moved the focus ring off it. Neither check could see them: one reads the palette, the other swept a page nobody was pointing at. Both measure states now — vien-state-09nov.md.

The hover edge has its own token, --vy-border-control-hover, because more visible means darker on white and lighter on near-black, so one value cannot carry it. Light is unchanged.

Accessibility

LabelThe <label> wraps the control, so no for/id pairing to get wrong
RequiredThe asterisk is visible; the control carries required
HintA sibling, not inside the label
ErrorOn blur, below the field, in red text — and the summary banner carries role="alert"
Searchtype="search", so the browser offers its own clear control
Hover and focusBoth edges clear 3:1 on every ground in both themes, and border:check sweeps all three states — see above
