Loader

src/ui/Loader.tsx · two exports: Loader and BusyOverlay.

When to use

SituationUse
A button's action is runningbusy on the Button — it puts a Loader in the icon slot
Work over data already on screenBusyOverlay
A first load, where nothing is on screen yetA skeleton, not a loader
The app bootingThe boot screen

**A skeleton answers "what will this look like?".** Once the user has seen rows, that question is answered — so a re-price dims what is there and puts an indicator over it instead.

Which type, and it is a real distinction

TypeLooks likeFor
pulsing (default)Three dots, no rotationInside a button or a cell. It holds still, so the control it sits in does not appear to spin
converging-spinnerRotatingA whole page or a blocking overlay, where rotation is the point: something is working and there is nothing else to look at
infinite-spinnerAlso rotatingNot used. Kept reachable so a third case does not have to reach past this file

Why this file is a thin wrapper and not a design

The customer's live bundle already ships k-loader — with sm/md/lg, the eleven theme colours, and all three animation types.

The indicator was never an open question. We simply did not have @progress/kendo-react-indicators installed, so the one thing the product already uses was the one thing we could not draw.

Kendo's type names are kept verbatim. Button maps MD3's variant ladder onto Kendo's fill modes because MD3 has a ladder worth keeping; a loader has no such vocabulary to reconcile, so inventing dots / spinner / ring here would be a second set of names for one set of things.

BusyOverlay

Dims what is on screen, puts a spinner and a sentence over it.

PropRule
labelWhat is happening, in words. It is shown and read aloud — "Updating results…", not "Loading"
blockingTrue when the user must not touch what is underneath

Two things it does that are easy to miss:

  • The content underneath gets aria-hidden while busy, so a screen reader does not read a table that is about to change.
  • When blocking, it also gets inert — the right word for this, which React 19 passes through. It is only honoured once the overlay is actually up, which is why both are set rather than either alone.

The label is the whole point

<Loader label="Working" />          // on a button
<BusyOverlay label="Updating results…">…</BusyOverlay>
Say what is loading, not that something is. Loading tells a screen reader user that the page is busy, which they already know from the fact that nothing is happening. Updating results tells them what to expect back.

Accessibility

Rolerole="status" with aria-live="polite" on the overlay — it waits its turn, unlike an error
Labelaria-label on the loader, and the same words visible under it
Underneatharia-hidden while busy; inert as well when blocking
Reduced motionHonoured — see B6. Reduced motion is a state, not a switch: things that fade in stay
