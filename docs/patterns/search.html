Search is not filter, and the list screen already draws that line

List screen settles the four ways to narrow a list. The half that belongs here:

A filter is for a set you are describing; search is for a record you can name. If a user is typing a part number into a filter, the search box is in the wrong place.

Which is why the toolbar order is filters → search → columns, and why the empty state has to say which of them emptied the list.

⌘K — the palette

The live menu holds 51 nodes, 47 of them destinations, behind a collapsed hamburger — so a new user must remember which of eight groups owns a screen before they can reach it. Search removes that requirement. Four scoring tiers, best first: a title that starts with the query, a title that contains it, the route, then the old name and the hint.

Three things it promised and did not do

All three were in the shipped build on 9 November, and all three are the same mistake: a search box describing a reach it does not have.

The route is the third name, and it was the one missing

Finding C1 records that every screen here has three names: the nav says Project Requirements, the browser title says Request for Quotation, and the route says quotation. C1 declines to pick one, on the grounds that choosing breaks the two that users already search for.

The answer to that is not to pick. It is to match all of them — so the path is a scoring tier, below both title tiers so a route match never outranks the name on screen.

rfq still finds nothing, and that is left alone. Neither RFQ nor Request for Quotation appears in any nav label or any route. Making them match would mean inventing a fourth name for 47 screens, which is the thing C1 refused.

One left edge

The group led each row, in a column set to a 66px minimum — which is a column that aligns nothing. Measured, the eight live group labels run from 88px to 199px, so the eight visible titles started at five different x positions, and Home — a leaf group with no label at all — started at a sixth.

Widening the column to 199px was the other way out, and it spends a third of a 620px palette on a qualifier that matters for the eight rows where a label repeats: Configuration appears 5 times in this menu and Reporting 3.

So the group moved to the end of the row and right-aligns. All eight titles now begin at one x.

A list you scan by name has one job for the eye: run down a single left edge.

The list toolbar — what a grid search actually reads

A column opts in with searchable: true. 18 columns across the six list screens do; the rest are dates, statuses and numbers, where a filter is the right control and a substring match is not.

Search runs before sort and paging, because sorting a page rather than a set would sort twenty rows out of two thousand.

Hiding a column used to hide the record

The search read the visible columns, so unticking one in the Column chooser silently narrowed what the list could find. Measured on Manufacturers:

Rows for SEMCO
Aliases column shown1 of 18 — Samsung Electro-Mechanics, whose only match is in Aliases
Aliases column hidden0, under Nothing matches "SEMCO"

The record was still in the list. The box was still captioned Search name, website or alias.

Two reasons that is wrong, and not a trade-off:

  • List screen defines Columns as which of the view's columns you personally show, held in your browser. A display preference must not change the answer to a question.
  • searchPlaceholder is a fixed string the page author wrote, naming the fields. It cannot know what you hid, so it goes on promising a field the search has stopped reading.

Search now reads the whole column set. The cost, stated: a row can match on a column you cannot see. That is the smaller harm — a hit you have to widen the view to explain, against a record the list told you does not exist.

Nothing until it is worth something

The two searches that reach across a whole record set wait before they answer.

AML SearchType at least two characters. A dialog that opens showing 600 rows invites scrolling; this one asks a question and waits
Caps at 60, and says which it is: First 60 matches or 12 matches
Where Part Number UsedZero is an answer, not an absence — nothing else consumes this part is the most useful thing the popup can say, and it says it rather than showing an empty table

Saying which emptiness this is

An empty result has to name its cause, because the user cannot see which of the three narrowings is doing the work.

SituationWhat the screen says
Search found nothingNothing matches "xyz" · Clear search
Search and a filter are both onBoth a search and a filter are narrowing this list.
Filters onlySay so, and offer Clear all
Nothing on file at allWhat this list is for, and the button that fills it
The earlier version offered to "clear the search to see all 0 records" when the search was empty and the filters were doing the work. An empty state that misnames the cause sends the user to undo the wrong thing.
